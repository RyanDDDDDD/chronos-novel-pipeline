# 剧情编排范式：解耦式叙事调度 (Decoupled Plot Design Paradigm)

## 1. 核心理念：Plot 作为“干瘪的事件流”

在 Chronos 高度解耦的架构中，`plot_library.json` 中的剧情描述（`description`）**不应当承担全能作家的职责**。

过去常犯的错误是在 Plot 中写入：
- **复杂的心理描写或人物介绍**（例如：“她极度自卑且畏缩地低下头”）。
- **极度具体的交互动作**（例如：“他一把攥住她的手腕，反剪到背后按在墙上”）。

**这种“写得太满”的 Plot 会致命地扼杀引擎的泛化能力**。因为在当前流水线中：
1. **Setup Chat + 角色档案** 负责注入人物的心理基底（Archetype、archive 状态）。
2. **构建期 skills**（`skeleton-expansion`、`beat-dialogue-design`）负责分镜、分 beat 与台词设计意图。
3. **主笔循环（dialogue mode）** 在预建任务包约束下流式落字；状态由 `derive_states` 滚动。

因此，Plot 存在的唯一目的，是提供 **“场景调度与人物站位 (Scene Staging)”**——供 Setup Chat 扩写骨架，而非直接驱动落字时的全部细节。

## 2. Plot 编写黄金法则：朴实简短的叙事过程

一个完美的 Plot 描述应该像电影导演给群众演员讲戏，只交代以下两点：
1. **表层事件/环境**：现在处于什么物理位置？外界在发生什么事？（如：在逛街、在吃饭、在整理行装）
2. **人物位置与掩护动作**：谁在明处？谁在暗处？大家在用什么理由做掩护？

### ❌ 错误示范（过度干预）
> “男主甲卑微地跪在首领面前，为了求得原谅，他一字一句地磕头认错，声音颤抖地念完早已想好的说辞，额头磕在青石地上闷响一声接一声。”

**错误原因**：把动作写死了（磕头、认错台词），把状态写死了（卑微求饶），后续 beat 设计与主笔任务包失去发挥空间，大模型只会枯燥地复述。

### ✅ 正确示范（纯粹场景调度）
> “男主甲在更衣室的全身镜前试穿远行的外衣。门外不时有下人走过。女角丁、女角戊和女角丙借着层叠的衣架和换衣屏风作为掩护，一边假装为男主甲递送衣物，一边低声交换着各自打探到的消息。每当门外有脚步声靠近，她们的神经就越发紧绷。”

**正确原因**：只交代了环境（镜前、门外有下人）、掩护（递衣服）、暗中事件（低声交换消息）。具体聊了什么、用什么动作、什么台词风格，留给 Setup Chat 分 beat 与主笔在任务包约束下现场发挥。

## 3. 高级技巧：滚动式的场景切换 (Rolling Locations)

为了充实文本体量并增加剧情的张力，在一个 Chapter 的连续 Stage 中，应当积极引入**微小但清晰的空间移动**。

以「离行之夜」一章为例，合理的动线设计：
- **Stage 1 (更衣室)**：试装时暗中交换情报。
- **Stage 2 (幽暗走廊)**：队伍转移时的短兵相接。
- **Stage 3 (宴会桌旁)**：表面端庄饮酒，桌下暗中传递密信。
- **Stage 4 (室外庭院)**：卸下防备后的坦诚对峙。
- **Stage 5 (客房)**：耗尽心力后的短暂休整与最终决意。

**优势**：空间移动顺理成章地更换人物站位，并为 Setup Chat 的 beat 分镜提供不同环境约束（如「靠墙压制」「隔墙有耳」等场景限定）。

## 4. 总结

在 Chronos 架构下写剧情，请记住十六字箴言：
**“不写心理，不写细节；只写站位，只写环境。”**

留白越多，构建期 skills 与主笔循环对撞出的火花就越丰富、越让人惊喜。
